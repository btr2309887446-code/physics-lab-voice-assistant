# 修正说明：后台信息串进字幕（`search_from_ragflow`）

> 针对 [现在的问题.txt](现在的问题.txt) 第 4 条反馈：
> “字幕里偶尔会出现 `search_from_ragflow` 这类后台信息”
>
> 修正日期：2026-10-18

---

## 一、根因（两条独立通路，都实际存在）

### 通路 A：工具状态被当成“学生说的话”推到设备

`core/providers/tools/unified_tool_handler.py` 在每次执行工具前，会往设备推：

```python
await send_display_message(self.conn, f"% {function_name}")
```

而 `send_display_message` 发的是 **`stt` 类型**消息：

```python
message = {"type": "stt", "text": text, ...}
```

`stt` 在协议里的语义是“学生语音识别结果”。固件照做，把它当用户发言刷到字幕条上
（`main/application.cc` 的 `stt` 分支 → `display->SetChatMessage("user", ...)`）。

**这条通路每次工具调用都会触发**，且因为本项目有“知识库预查”（每轮提问前先直接调一次
`search_from_ragflow`），实际频率比想象中高。

> 两个客户端表现不一致，容易漏掉：
> - Flutter 端专门识别了 `% ` 前缀，映射成“🔍 正在查询知识库…”，所以**看着正常**；
> - ESP32 端没有任何过滤，**直接显示原文**。
> 学生手里拿的是 ESP32，所以他看到了。

### 通路 B：流式工具调用文本漏进 TTS / 字幕

`core/connection.py` 旧代码：

```python
if not tool_call_flag and content_arguments.startswith("<tool_call>"):
    tool_call_flag = True
```

只要模型输出的**第一个字符**不是 `<`，`startswith` 就永久为假，于是整段
`{"name": "search_from_ragflow", ...}` 被推进 TTS 队列。设备字幕取自 TTS 句子
（`send_tts_message(conn, "sentence_start", text)`），所以 JSON 也会显示出来。

触发条件（任一即可）：

| 场景 | 旧行为 |
|---|---|
| 模型先输出一个换行再输出 `<tool_call>` | 全段 JSON 进字幕 |
| 模型先说话再调工具（`好的，我查一下。<tool_call>…`） | 全段 JSON 进字幕 |
| `<tool_call>` 被拆成多个 chunk（`<to` + `ol_c` + `all>`） | 前半个 `<tool_` 进字幕 |

这解释了为什么学生说“**偶尔**”——标准格式不漏，带前缀或跨 chunk 才漏。

### 通路 C（附带发现）：运维话术被念出来

`plugins_func/functions/search_from_ragflow.py` 出错时返回 `Action.RESPONSE`，
而 `_handle_function_result` 会把 `Action.RESPONSE` 的内容**直接送进 TTS**。所以学生
可能听到“RAG接口返回异常（错误码：…）…解决方案：请检查RAGflow服务状态和网络连接”。

## 二、改了什么（7 个文件）

### 服务端（改完立即生效，**不需要重刷固件**）

| 文件 | 改动 |
|---|---|
| `core/handle/sendAudioHandle.py` | 新增 `send_tool_status_message()`，用独立 `tool` 消息类型；`send_display_message` 加注释警告勿用于内部状态 |
| `core/providers/tools/unified_tool_handler.py` | 不再拼 `"% 函数名"`，改调 `send_tool_status_message()` |
| `core/connection.py` | 新增 `classify_stream_prefix()`；工具调用标记改为**任意位置**匹配；流式开头加 holdback（压着不播，确认非工具调用再放行）；解析失败的 JSON 不再写进对话历史；补一条兜底回复避免静默 |
| `plugins_func/functions/search_from_ragflow.py` | 所有错误分支改成学生话术，运维细节只写日志 |
| `core/providers/llm/system_prompt.py` | 修工具调用示例里写错的闭合标签 `<tool_call>` → `</tool_call>`（**这是通路 B 的诱因之一**：提示词自己给了个错误示范，模型自然学着输出不规范） |

### 固件（需重刷，作为**独立**的第二道防线）

| 文件 | 改动 |
|---|---|
| `main/application.cc` | `stt` 分支过滤 `% ` 开头的旧版工具状态；新增 `tool` 类型分支（只记日志，不进字幕） |

> 固件这层单独看也有价值：**如果只想刷固件、不动服务器**，也已能修好通路 A。

### Flutter 客户端

| 文件 | 改动 |
|---|---|
| `lib/services/xiaozhi_service.dart` | 新增 `case 'tool'`，继续显示友好提示；保留 `% ` 兼容分支 |

## 七、顺带发现、但本次没改的问题

1. **知识库预查失败时学生得不到提示**：`connection.py` 里 RAGFlow 返回
   `Action.RESPONSE`（接口报错）时，只记日志、不设 `kb_precheck_failed`，
   所以 `kb_failure_mode` 的三档兜底**不会生效**，学生这边表现为“没有任何提示地裸答”。
   要一并纳入兜底，把那个分支改成 `kb_precheck_failed = True` 即可——但会改变现有的
   兜底语义，建议单独评估。

2. `system_prompt.py` 第 75 行有个 `\`` 无效转义（Python 3.13 启动时会打
   `SyntaxWarning`）。不影响功能，顺手改成原始字符串即可消掉。

3. 字幕本身的问题（单行循环滚动 + 每条整行替换）是这次“看不清”的根源，但属于
   另一条线，见对话记录中的建议。
